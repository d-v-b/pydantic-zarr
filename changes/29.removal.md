A field that a subclass adds to a node, computed fields included, must now be a valid extra field of the node's metadata document. In `pydantic_zarr.v3`, it must be an object with `"must_understand": false`, or a field that the scope claims. So `label: str` is rejected, and so is `consolidated_metadata: dict | None = None`, because `null` is not valid consolidated metadata. In `pydantic_zarr.v2`, a group subclass cannot add a field, because a `.zgroup` document holds only `zarr_format`. To keep a field out of the document, declare it with `Field(exclude=True)`. Previously, any added field was accepted, and then lost or rejected when the hierarchy was written and read back.

`from_flat_group` is now `GroupSpec.from_flat`. Its members are plain specs, validated in the default scope, with the fields their classes add in `extra_fields`. So a hierarchy whose fields only a member class's scope claims is now refused by `from_flat_group` and by the plain `GroupSpec.from_flat`. Read it with its own class instead. Previously, `from_flat_group` kept each array member's class and dropped the fields that a group's class adds.

`from_flat` and `from_flat_group` now raise `ValueError` for a node under an array, and for a key with an empty segment, such as `"//b"`. `from_stored_metadata_json` now raises `ValueError` for a group document with a `members` key. An extra field may no longer use a field's alias or a computed field's name as its key. Previously, a node under an array was silently dropped, and `"//b"` could replace `"/b"`.
